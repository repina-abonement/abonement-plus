# Telegram: транспортные отказы, стикеры и проверка связи

## Подтверждённые сведения и границы

Пользователь показывает No route to host при импорте набора и общий Telegram: ошибка 403 при отправке. Сообщение без Telegram-description не позволяет утверждать, что клиент заблокировал бота. В deploy/relay /tg/ защищён allow конкретного CRM_IP; после изменения исходящего адреса возможен 403. Реальный адрес, настройки/логи production и получатель ошибочной попытки не прочитаны, эта причина остаётся гипотезой. Публичные корни репозиторного моста и api.telegram.org ответили HTTP 200 из облачной среды, а не с CRM.

## Реализация

TelegramTransportError отличает сеть/HTTP без API-description от настоящего отказа Telegram. В сообщении о 403 моста предлагается проверить разрешённый IP; для недоступной сети указано, какой маршрут не работает. Описания Telegram сохраняются с редактированием токена, HTML прокси не отображается как API-описание. Отправки sendMessage/sendSticker/sendPhoto не повторяются автоматически и не переключаются на другой маршрут.

Только getStickerSet/getFile и скачивание публичных превью могут перейти с отказавшего моста на официальный Telegram. Поддержаны транспортная ошибка маршрута и сетевой отказ скачивания. При отказе обоих маршрутов возвращается объяснение сети без ключей/URL бота. Настоящий Forbidden с description не повторяется этим fallback.

GET /api/integrations/telegram/diagnostics, admin only: getMe через сохранённый мост и напрямую. Не передаёт chat_id/text, не отправляет сообщений, не меняет webhook/настройки, не возвращает токен/секретный URL/HTML. В Настройки → Связь с клиентами → Telegram добавлена «Проверить связь», читает сохранённое подключение; «Сохранить и подключить» не вызывается.

## Следующая рабочая проверка

1. Руководитель запускает «Проверить связь» и передаёт две строки результатов; ключи не присылаются.
2. При 403 моста оператор сервера сверяет фактический исходящий IP CRM с allow в /tg/ и состояние моста. Не делать мост общедоступным; не передавать полные nginx-строки с URL бота/токеном.
3. Если getMe доступен, а отправка возвращает настоящий отказ Telegram, проверить точный тип Telegram-диалога, business_connection_id/права бизнес-бота и API-description. Не маскировать это сетевым fallback.
4. Пользователь явно разрешила один тест на точно указанной в беседе семейной карточке с её личным контактом. Перед действием сверить карточку, родителя, канал/номер и получателя, не пробовать на других клиентах. Имя ребёнка и номер в публичный отчёт не включаются.

Авторизованный браузер недоступен из-за отрицательного баланса TinyFish; SSH-ключей/серверных секретов в среде нет. Рабочая тестовая отправка и живой импорт набора не выполнены, сетевые настройки не менялись.

## Проверки

Пройдены семь test_telegram_transport, два test_sticker_relay_fallback, test_sticker_packs, test_comms, compileall/JS syntax/diff. Проверены транспортный HTTP 403, настоящий Forbidden, сеть без раскрытия токена, строго getMe и отсутствие записей диагностики, fallback только чтения/файла и двойной сетевой отказ; отправка выполняет ровно один запрос. Chromium 390/1440: GET-only диагностика двух маршрутов, ошибка/повторная попытка, отсутствие connect/save/send и переполнения; регрессия приветствия. Публикация/публичный JS проверяются отдельно, это не доказательство восстановления связи.
