# Дата оплаты и первый месяц после ПУ — 17 ноября 2026

## Подтверждённые требования

Юлия уточнила: абонемент был оплачен картой на филиале 16 ноября, а вносится позже. В обычной форме нужна фактическая дата оплаты для финансовых показателей. После ПУ по умолчанию отмечены занятия строго после даты ПУ в этом месяце; администратор может выбрать ранние реальные занятия вручную

## Реализация

- Поле фактической даты в расчёте и в форме записи полученных денег; расчёт скидки/надбавки и платёж используют выбранную дату
- День оплаты сохраняется в payments.paid_at, время внесения остаётся в payments.created_at. Для полной ручной оплаты дата subscriptions.paid_at учитывает фактические связанные платежи. Старые платежи не передатируются
- Запись картой на филиале — card_branch. Для прошлой даты создаётся запись уже полученных денег; новую ссылку на оплату для такой даты интерфейс не предлагает. PayKeeper по-прежнему зачисляется по исходному банковскому платёжному событию
- Кнопка «Отметить оплату» открывает поля без создания нового счёта; счёт появляется при подтверждении. Повторы одного запроса оплаты идемпотентны по request_id; частичные оплаты сохраняют остаток
- Для первого месяца с отмеченным ПУ ранние занятия и день ПУ исключены по умолчанию. Полный календарь расписания остаётся доступным для ручного включения. Состав отправляется явно, в том числе пустой список исключений через dates_selected, чтобы HTTP-парсер не возвращал его к автоматическим значениям
- Цена/даты проверяются сервером при записи. Дата в будущем запрещена, реестр/история сохраняют время внесения. Прежние счета, оплаченные абонементы и продления массово не пересчитывались

## Проверки

Тесты: 4 новых сценария даты/денег, существующие paylinks/payment_quote, историческая покупка, отметка ПУ, обязательные данные, pricing, money, program_transfer, single_sale. Проверены разделение дат, карта на филиале, защита от повтора и изменённого повторного payload, частичный остаток, запрет будущего дня, отсутствие записей при preview

Chromium с локальным HTTP и синтетической БД: 4 занятия после ПУ 16.11, ручное включение пятого и снятие обратно, расчёт на 16.11, изменение даты прямо у суммы оплаты, отсутствие счёта при открытии формы, однократная запись платежа картой 16.11 и оплаченного абонемента. Ошибок JS нет

Пример 5 120 ₽ в тесте — синтетический расчёт четырёх занятий по 1 600 ₽ со скидкой 20%, не подтверждение суммы настоящей оплаты Матвея. Реальная рабочая покупка/платёж не вносились, сумма фактической оплаты пользователем не сообщена отдельно
