# Действующие статусы и задачи ERP — снимок 21.11.2026

## Что подтверждено

Источник — прочитанные под ролью руководителя настройки ERP Футболики для территории «Солнцево (Москва)» и штатный журнал событий задач. В ERP и CRM при сборе сведений ничего не менялось.

- 11 системных и 11 пользовательских статусов посетителей;
- 16 шаблонов задач;
- 5 175 событий с дедлайнами 01.10–31.12.2026;
- 2 078 уникальных ID задач в частичном реестре;
- 137 событий завершения и 51 событие архивирования в доступном диапазоне.

Исходные клиентские XLSX не хранятся в публичном репозитории: в них есть имена, комментарии и рабочие ID.

## Системные статусы ERP

| Статус | Подтверждённое условие |
| --- | --- |
| Новый лид | добавлен новый посетитель |
| Записан на ПУ | добавлено пробное; нет абонемента на текущий или будущий период |
| Был на пробном, не купил абонемент | положительная отметка ПУ; нет текущего/будущего абонемента |
| Не пришел на пробный урок | отрицательная отметка ПУ; нет текущего/будущего абонемента |
| Новый оплативший посетитель | покупка текущего месяца, раньше покупок не было |
| Постоянный посетитель | абонемент был в прошлом и куплен в текущем месяце; не только разовые |
| Вернувшийся | покупка была раньше, в прошлом месяце отсутствовала, в текущем есть |
| Не оплачен текущий месяц | абонемент был в прошлом месяце и отсутствует в текущем |
| Нет абонемента | нет абонемента в прошлом и текущем месяце |
| Ходит разово | постоянный посетитель, покупавший только разовые занятия |
| Куплен на будущий период | текущего абонемента нет, будущий куплен |

Пользовательские статусы: «Думают», «Не удалось связаться», «Лист ожидания», «Клиент отказался», «Ушедший», «ОПЕРАТОРУ», «Взрослый ребенок», «Новопеределкино», «Пыхтино», «Вечный недозвон», «Разовик».

Два шаблона «Как прошло ПУ?» нельзя объединять: порядок и набор исходов различаются. Повторный выбор того же названия разрешён для части задач, но настройки не доказывают, создаётся ли новый ID и от какой точки считается фактический следующий звонок.

## Граница автоматизации

Подтверждённую матрицу названий, событий, исходов и дедлайнов можно воспроизвести в CRM. Нельзя додумывать число попыток недозвона, интервал повторного звонка, автоматическую смену пользовательского статуса, судьбу прежней задачи при переносе ПУ или объединять два одноимённых шаблона.

Частичный реестр нельзя массово применять к карточкам: колонка `ID` — ID задачи, а не ERP ID ребёнка. Надёжно проверена только одна связка; остальные имена и комментарии недостаточны для безопасной идентификации. Для массового переноса нужен реестр с ERP ID ребёнка/лида и подтверждённым текущим состоянием каждой задачи.

## Расхождения текущей CRM

Собственная лестница CRM «завтра → 3 дня → неделя → месяц», автоматический перевод после числа недозвонов, «дожим» ровно в три попытки, возврат отказников через три месяца и оживление старых лидов не подтверждены этим снимком ERP. Для карточек с ERP ID они уже отключены переходным режимом. Для новых карточек CRM замена должна выполняться отдельной проверяемой миграцией цепочек, без изменения денег, абонементов и посещений.
