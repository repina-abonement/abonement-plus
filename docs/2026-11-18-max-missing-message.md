# CRM-153 — пропавшее входящее MAX

Ориентир пользователя: Руфина, 18.11.2026 12:55 МСК, сообщение видно в Wazzup, не видно/не ищется в CRM. MAX chatId из показанного URL: 181742783, канал: 2a291237-241a-4b14-a557-9b44a3e6a7e9. Номер 79916150960 в шапке относится к школе, не использовать как телефон клиента

Подтверждённые локальные дефекты: ошибка обработки Wazzup откатывалась с ответом HTTP 200; запоздалый ответ поиска мог перезаписать более свежий. Исправлены, но их связь с конкретным сообщением пока не доказана

25 серверных тестов и Chromium-тест гонки поиска пройдены. Отдельные существующие сценарии MAX и телефонного поиска пройдены. Все тестовые сообщения и БД синтетические. Клиенту ничего не отправлялось

## Уточнение после первого отчёта Work

Кандидат messageId из DOM Wazzup: b50aac52-b4c7-4013-b81f-e6420f70b9e6. Соответствие data-id полю вебхука пока не подтверждено. Work нашёл активный диалог Руфины, но не исходное сообщение за 12:55. Сообщение за 13:06 ранее названо входящим ошибочно: по подтверждению Ольги оно отправлено ею из CRM, не дожидаясь появления сообщения клиента. Это не доказательство работоспособности входящего вебхука

Добавлен административный GET /api/integrations/wazzup/message-trace. По точному message_id ищет сохранённые сообщения и события; показывает направление, попадание в текущую историю/последние 200 сообщений, статус удаления. Сопоставляет только точные поля JSON, без поиска подстрокой в тексте сообщения. Отдельно показывает до 20 событий заданного chatId в пределах сохранённого журнала, чтобы проверить различие ID интерфейса/вебхука. Диагностика не отправляет запросы провайдеру, не изменяет привязки и не снимает непрочитанное. В ответе нет текстов сообщений/телефонов/ключей

GET /api/integrations/log?id=НОМЕР теперь позволяет руководителю открыть конкретное найденное событие, даже если оно уже за пределами последних 30 строк интерфейса. Данные журнала ограничены сроком хранения; пустая выборка не доказывает отсутствие доставки
