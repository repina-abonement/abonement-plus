# CRM-151 / CRM-164 — СБП по QR ID вместо имени банка, 19 ноября 2026

## Рабочее наблюдение и причина

Юлия передала результат авторизованной проверки Work: по PayKeeper №11534 / CRM8199 / 1350 ₽ в выписке Точки найдено зачисление с ID `cbs-tb;2672919318;1`. Назначение: «Зачисление по QR коду ID AD2010208UGANCGD8TRACRVL5JPQOK71 от 18.11.2026. НДС не предусмотрен.». Этот QR ID совпадает с `bank_payment.unique_id`. Отправитель — ООО «Банк Точка», а не ФИО клиента. Предыдущий алгоритм использовал только имя/сумму/день и проигнорировал уже сохранённый точный банковский идентификатор: это ошибка выбранного сопоставления, а не нехватка права ReadAcquiringData.

По тому же отчёту источник PayKeeper за 18 ноября вернул полный список одной оплаты СБП, без карточных оплат. За 19 ноября список недоступен, причина старым ответом не раскрыта; отсутствие карточных оплат за 19 ноября НЕ установлено. ОФД вернул 403 Kkt is not paid, первичные реквизиты чека известны. Новый код не устраняет внешний отказ ОФД и не превращает подтверждение банка в полный успех.

## Исправление

- Приоритет СБП: точный QR ID из банковского назначения или структурированный банковский идентификатор, сумма, Booked/Credit/RUB, единственный кандидат и единственное распределение проводки. ФИО отправителя при точном ID не требуется
- Идентификаторы читаются из полного дневного списка и уже проверенного кэша конкретного PayKeeper-платежа (`bank_payment.unique_id`, SBP IDs). Кэш принимается только при совпадении provider_payment_id, id и суммы, available=true; привязка к CRM по прежнему проверяет заказ и сумму
- Регистр и полный токен ID сохраняются: префикс, суффикс, похожий ID или другая сумма не дают подтверждения. QR-совпадение допускает отражение банком на следующий день: имя/дата не заменяют точный ID и сумму
- Если в назначении явно другой QR ID, алгоритм не откатывается на слабое совпадение имени. Если одна проводка соответствует нескольким точным ссылкам или уже отдана другой оплате, успех не выставляется. Точное совпадение имеет приоритет над совпадением имени
- Подтверждение хранит метод, поле источника, поле выписки, совпавший ID, ID банковской операции, сумму и дату отражения. В деталях «Оплат» показывается связь QR ID / ID операции → проводка
- Для неподтверждённой оплаты `match_diagnostics` раскрывает известные поля идентификаторов, количество кандидатов по ссылке/имени и конфликты QR. Причины неоднозначности/занятой проводки сохраняются отдельным текстом
- Для дневного списка PayKeeper сохранены очищенные HTTP-статус/сообщение, этап, код ошибки валидации и безопасная форма ответа. Диагностика различает неизвестную схему, неправильный день/дату/сумму, повтор IDs, предел страниц и ошибку поставщика. Последний полный состав при сбое остаётся сохранённым
- Старые недоступные дни без объяснения приоритизированы для повторной диагностики. Новая версия сопоставления однократно планирует ближайшую проверку PayKeeper/банка после обновления; обычный интервал остаётся автоматическим, ручной финансовый запуск не нужен
- Защищённый GET control-payment теперь возвращает `payout_control.matching_version=2` и `sbp_reference_matching=true`

## Проверка

124 профильные проверки пройдены, включая fixture-наборы: точная строка назначения и банковский ID из сообщения Work, отправитель-банк без ФИО, следующий день отражения, ошибочная сумма, префикс/суффикс/регистр ID, два банковских совпадения, приоритет точной ссылки, структурированный paymentId. В регрессии №11534 получает bank.confirmed, а отказ ОФД сохраняет ofd.unavailable и общий attention. Количество оплат не меняется. Проверены безопасные подробности HTTP-ошибки и неизвестной схемы дневного списка, сохранение состава при сбое; legacy fiscal exit 0, синтаксис Python/JS и diff-check пройдены. Chromium настоящего money.js проверил раскрытие QR ID и банковской проводки; дополнительно пройдены 3 адресные проверки №11534 и ошибок источника после уточнения неизвестных количеств.

Это код и локальное воспроизведение предоставленных рабочих данных. Реальный статус CRM после публикации и следующего серверного прохода ещё должен быть прочитан. Новых счетов/оплат/возвратов/чеков/сообщений клиентам и изменений доступов не выполняли. API эквайринга Точки не используется. Карточное пакетное зачисление на реальных данных ещё не проверено: за 18 ноября карточных оплат нет, а за 19 ноября требуется объяснённый ответ источника.


## CRM-151 / CRM-164 — сначала факты CRM, затем внешняя сверка

Последнее прямое уточнение Юлии: сначала смотреть наличие продаж/оплат в CRM. Предыдущий refresh_source ошибочно включал последние 7 календарных дней независимо от записей CRM; поэтому предупреждение по 19 ноября не было обосновано проверкой CRM. Нельзя называть это отказом PayKeeper без проверки, требовался ли запрос вообще.

- **Код:** очередь дней берётся только из активных положительных оплат CRM, относящихся к PayKeeper (метод/существующая привязка). День без таких оплат не запрашивается. Наличные, отменённые и отсутствующие оплаты не инициируют PayKeeper-проверки
- **Нормальное отсутствие работы:** сервер возвращает no_crm_payments / no_payments, а дневная диагностика — not_required, check_required=false, crm_payments=0. Старое предупреждение календарного запроса не показывается активной ошибкой, история не удаляется
- **Если оплаты CRM есть:** остаются автоматические PayKeeper → банк → ОФД. Пустой штатный список [] — успешное чтение нулевого списка, а не сбой; результат сопоставляется с фактической обязанностью CRM, не доказывает зачисление. Неизвестный/ошибочный ответ диагностируется только для требующего сверки дня
- **Защита и наблюдаемость:** bank run и карточное представление также ограничены днями CRM. payout_control возвращает matching_version=3, crm_first=true, crm_payments и check_required по дням. Для №11534 сохранён приоритет точного QR ID с суммой; ОФД проверяется независимо
- **Рабочий факт:** фактическое число оплат CRM за 19 ноября из доступного ответа ещё не получено. Новый код определяет его по БД, не делает предположение «оплат не было» или «PayKeeper недоступен»

Публикация и новая рабочая проверка отдельно от локальных тестов. ReadAcquiringData не требуется. Проведение новых оплат/счетов/возвратов/чеков не выполняется.

Проверка CRM-first: 129 профильных проверок пройдены после изменения очереди, ещё 2 адресные проверки подтверждают нормальные серверные циклы без оплат и подавление старой календарной ошибки. Проверены отсутствие запросов к PayKeeper/банку без оплат CRM, единственный запрос за действительный день, исключение наличных/отменённых, ручной способ PayKeeper без исходной привязки и сохранение QR-сопоставления. Фактическое отсутствие оплат за 19 ноября не объявляется без чтения БД рабочего сервера.
