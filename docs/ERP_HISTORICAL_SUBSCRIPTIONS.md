# Исторические абонементы и посещения ERP

Перенос выполняется через «Настройки → Перенос из ERP → Исторические абонементы и посещения». Сначала выбирают период и запускают предпросмотр. Запись разрешена только при единственной карточке и однозначном соответствии каждой группы по дате, времени и названию.

Исторический абонемент хранится отдельно от финансовых покупок CRM. Из ERP обязательно переносится его фактическая стоимость (`subscription.price`) для аналитики продаж по группе и месяцу. Эта сумма не создаёт оплату, счёт, долг, баланс, возврат или чек и не считается подтверждением способа оплаты. Если точной стоимости в источнике нет, запись остаётся на сверке: цену нельзя вычислять по текущему тарифу или числу занятий.

При переносе историю платежей не сверяют. Пустая история денег по историческому абонементу ожидаема. Она не требует поиска чеков или операций в PayKeeper, постановки задачи администратору либо отметки о долге.

Подтверждённые отметки переносятся только по исходным датам. Пустая отметка игнорируется и не превращается в пропуск. Старая отработка сохраняет фактические дату, время и группу без выдуманной связи с пропуском. Повторный запуск сверяет исходные ID ERP, включая стоимость, и ничего не дублирует.

При частично известной посещаемости JSON хранит полный подтверждённый план каждого абонемента в `subscriptions[].schedule`, а `attendance` содержит только фактические поимённые отметки. Число строк плана должно совпадать с `lesson_count`. Прошедшее занятие без отчёта не становится ни посещением, ни пропуском; будущие строки плана остаются запланированными. Поздний повтор с новой отметкой добавляет её поверх существующего плана, не создавая абонемент повторно.

Для отметки из Telegram используются `source_message_id` и при наличии `source_chat_id` и/или `source_message_url`. Поле `erp_attendance_id` для неё остаётся пустым: CRM формирует только внутренний ключ дедупликации посещения и не выдаёт его за ID ERP. Telegram-сообщение — общий источник, а не уникальное посещение: один групповой отчёт может подтвердить несколько детей и несколько занятий. Поэтому внутренний ключ дополнительно учитывает ребёнка, абонемент, дату, время и тип занятия. Повтор той же отметки того же ребёнка ничего не добавляет. Ранее записанный ключ старого формата распознаётся только при совпадении ребёнка и фактического занятия.

При сопоставлении группы возрастные числа в названии значимы: например, `ПУП 6–8` нельзя объединять с `ПУП 9–11`. Если филиал, день и время всё равно дают несколько групп, предпросмотр показывает их названия и ID. Неоднозначность разрешается по исходной продаже/абонементу ERP; название журнала после слова «журнал» само по себе не доказывает фактическую группу занятия.

Для массового этапа выгрузка должна содержать контрольные итоги ERP по каждому месяцу, филиалу и группе: количество абонементов и их общую стоимость. Дашборд показывает рядом итог ERP, итог CRM и разницу. Перенос месяца не считается завершённым, пока разница не равна нулю по каждой группе; спорные и ещё не перенесённые строки входят в показанную разницу. Сверка относится к стоимости проданных абонементов, а не к способам и датам поступления денег.

Сопоставление карточек рассчитано на массовый перенос и не требует последовательного ручного выбора. Порядок автоматического поиска: точный ERP ID в карточке; ранее сохранённая техническая связь; точное совпадение полного ФИО ребёнка, даты рождения и телефона родителя. Поэтому выгрузка карточек обязана сохранять ERP ID, а при его отсутствии — все три проверочных поля. Одна фамилия не является основанием для объединения. Несколько кандидатов попадают в отдельный список сверки и не мешают обработке однозначных карточек.

Ручной выбор разрешён только как разовое подтверждение спорной связи во время пилота. Сервер повторно сравнивает полное ФИО. После успешного переноса подтверждённая пара `ERP ID → карточка CRM` сохраняется в техническом реестре, поэтому этот ребёнок при следующих месяцах и повторных запусках определяется автоматически.

Рабочие пилоты ограничиваются заранее согласованной парой ребёнок/период. Персональные строки контрольных выгрузок в репозитории и тестах не хранятся; проверки используют обезличенные данные.

При расхождении сведений о покупке приоритет у подтверждения СЗ. Если продажа отсутствует в ERP, перенесите подтверждённые в СЗ абонементы в карточку ребёнка с указанием источника СЗ. Для такой записи сохраняйте отдельный идентификатор источника, сумму и расписание каждой группы. При сверке истории платежей не создавайте повторные оплаты или чеки. Посещения вносите по фактическим отметкам. Если после проверки СЗ и отчётов тренеров остались спорные даты, перечислите их в ручной задаче на ближайшую рабочую смену
