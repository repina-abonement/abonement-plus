# CRM-164 / CRM-151 — контроль всех записей оплат, непрерывный PayKeeper и отложенное зачисление

Юлия требует целевой результат: в CRM должен работать контроль всех оплат и их фискализации, без остановок на объяснениях. PayKeeper нужно проверять по каждой операции; Точка нужна для фактического поступления на счёт. Выплата может объединять дневные операции и приходить позднее; конкретный график выплат пока не подтверждён.

## Изменения

- В «Оплатах» все строки выбранного периода/способа получают read-only контроль: исходная операция, банковское зачисление, ОФД. Для отменённых записей отдельное исключение, для отрицательных корректировок/возвратов отдельная необходимость проверки.
- Сводка показывает число подтверждённых и требующих внимания, фильтр открывает последние. Нет скрытого пропуска вручную внесённых/непривязанных оплат: для них явно отсутствует доказанная связь.
- Данные контроля строятся из локального кеша без HTTP-запросов при открытии таблицы; чтение не создаёт оплат/чеков/переносов. Раздел обновляется раз в минуту, если видим, карточка клиента закрыта и подробности контроля не раскрыты.
- Автопроверка PayKeeper теперь повторяет чтение и для уже подтверждённых чеков: прежнее исключение таких записей мешало отслеживать последующие изменения и возвраты. Интервал/ограничение очереди сохраняются. В кеш сохраняются безопасные поля результата точного payment ID/заказа/суммы и ошибка ОФД; наличия одного чека недостаточно для общего успеха.
- Точка читает выписку от даты операции до текущей московской даты с ограничением одного окна 31 день; ранее читался только день исходной оплаты, что не охватывало зачисление на следующий день. Ограниченное покрытие явно отмечается. Не предполагается срок выплаты один день, выходные включены. Поиск пока даёт кандидатов, а не положительный итог зачисления.

## Проверки

53 профильных теста пройдены: все ручные способы, пустой период, контроль без записей в БД, неверный/возвращённый исходный PayKeeper, отсутствие ложного банковского успеха, полная фискальная идентичность ОФД, повторная проверка уже успешного чека, выписка на последующие дни/выходные и предел окна. Отдельно тесты деталей платежа и старый сценарий test_money пройдены. Chromium настоящего money.js с синтетическим API: сводка, фильтр требующих внимания, раскрытие причин без случайного открытия клиента, сохранён переход из имени клиента.

## Незавершённая часть и внешние ограничения

Это рабочая заготовка контроля и охвата, не завершение всей интеграции. Положительное банковское подтверждение пока не реализовано. Нужна проверка реальной структуры реестра/выплаты и связь всех её строк, возвратов, комиссии и нетто с проведённой банковской операцией по надёжным ID; сумма/имя/дата не доказывают связь.

По последнему отчёту Work: Точка 403 ReadAcquiringData и ОФД 403 Kkt is not paid остаются; исправление доступов не подтверждено. Без них нельзя получить требуемое рабочее доказательство. Фоновый опрос в рабочей CRM подтверждён Work, но данная новая сводка и изменения после публикации требуют авторизованной проверки.

Сбер не подключён, ручные оплаты не имеют автоматической точной связи с исходным платежом/чеком, пакетное зачисление не подтверждается автоматически, покрытие всех касс/истории/пагинации остаётся незавершённым. Реальные деньги/чеки/настройки/клиентские сообщения в этой доработке не изменялись.


CRM-151 / CRM-164, исполнение до результата: Юлия требует самостоятельно вести весь цикл, запрашивать только необходимые внешние действия и не останавливаться на констатации незавершённости. Проверка инструментов текущей сессии не обнаружила доступ к авторизованным кабинетам/локальному Edge или прямые коннекторы Точки/PayKeeper/ОФД/Сбера. Через async запрошен вход владельца в Edge в Точку, ОФД и СберБизнес, без передачи паролей/токенов. Ответ пока не получен.

19 ноября напрямую прочитана официальная документация Сбера: https://developers.sber.ru/docs/ru/sber-api/specifications/statement/statement-overview и /statement/transactions, /statement/transactions-id. Выписка требует GET_STATEMENT_ACCOUNT, операция — GET_STATEMENT_ACCOUNT и GET_STATEMENT_TRANSACTION; документация требует постраничного чтения, история предыдущие 5 лет плюс текущий год. Это проверка документации, не рабочее подключение. Документация Точки прямым HTTP в этой сессии недоступна. Во вторичной сохранённой OpenAPI block.paymentId описан лишь как уникальный идентификатор платежа, а не доказанный идентификатор общей выплаты: приравнивать его к банковской выплате без рабочего контракта нельзя. Реестры/комиссии/возвраты и связь с проводкой остаются обязательным входом.
