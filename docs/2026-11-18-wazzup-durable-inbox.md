# CRM-154 — сохранение входящих Wazzup до обработки

Юлия разрешила исправление после разбора пропавшего сообщения Руфины. Новая схема: аутентифицированный POST полностью сохраняется отдельно от основной БД, и только после фиксации CRM отвечает 200. Фоновый процесс добавляет событие в основную CRM и повторяет при ошибках. Занятость основной SQLite не мешает сохранению в отдельной очереди

## Подтверждённый инцидент CRM-153

В переданном владельцем серверном журнале 18.11.2026 в 12:56:07 МСК обработчик POST /hooks/wazzup/... упал на BEGIN IMMEDIATE с sqlite3.OperationalError: database is locked и вернул 500. Сбой произошёл до обработчика ошибок/записи hook_log. Одновременно блокировка мешала recents, планеру, задачам и AI-worker. Держатель блокировки этим фрагментом не установлен. В 12:55:04 сервис перезапущен; точный источник перезапуска журналом не установлен. ID сообщения в строках сервера не печатается, сопоставление с конкретным сообщением опирается также на сведения Wazzup

Поддержка Wazzup подтвердила баг #2186121 — повтора не было. Ручная повторная отправка ими не поддерживается; они предложили восстановить данные из ранее присланного лога. Исходное полное событие ещё не получено. Старое сообщение Руфины не восстановлено, ничего клиенту не отправлено, данные из скриншота не выдумывались

## Реализация

- crm/wazzupqueue.py хранит полный JSON в отдельном файле рядом с основной БД: <путь_БД>.wazzup-inbox.sqlite3, режим 0600. FULL synchronous, secure_delete. Payload и ключ авторизации вебхука не выводятся в диагностике; секрет пути не сохраняется в событии
- Проверка действующего hook_token остаётся до сохранения. Неверный ключ получает 403, повреждённый JSON — 400. Ошибка сохранения/диск/лимит очереди — 503, без ложного «принято»
- Дедупликация полного события по SHA-256 канонического JSON. Разные изменения статуса/редактирования с тем же messageId не теряются как дубли всего события
- Worker автоматически стартует с CRM, просыпается сразу после нового события и проверяет ожидающие примерно раз в секунду. Временные ошибки соединения с БД также повторяются
- Основная запись события атомарна: сообщения/изменения и hook_log фиксируются вместе. Захват основной базы не ждёт блокировку, событие остаётся в очереди. Повторные попытки через 2–60 секунд, без удаления из-за числа ошибок
- Лизинг обработки защищает от двух обработчиков. После аварии незавершённая попытка доступна повторно через 120 секунд. Авария после COMMIT основной БД до отметки выполнения даёт повторную обработку с существующей дедупликацией сообщений
- После успешной обработки полное содержимое удаляется из очереди; технические квитанции и messageId хранятся 7 дней. Необработанные события автоматически не удаляются
- Лимит ожидающих payload: 256 MiB. При превышении новые события не подтверждаются как сохранённые. Это не защищает от недоставки самого HTTP-запроса или физической потери сервера
- Очередь переживает перезапуск приложения на том же диске. Существующий backup_once сохраняет основную БД; отдельный файл очереди не добавлен в существующую внешнюю резервную копию. При ручном переносе/восстановлении сервера учитывать этот файл, не удалять ожидающие события
- /api/integrations/wazzup/diagnostics показывает pending/retrying/oldest без текстов. Трассировка message-trace видит квитанцию даже до основной записи и возвращает saved_waiting_for_processing. Неисправность чтения очереди не уничтожает доступные результаты основной диагностики
- В чатах после 30 секунд ожидания появляется короткое сообщение о сохранённых входящих, которые ещё обрабатываются. Ошибка хранилища отражается отдельно. Обновляется обычным опросом счётчиков, без технических действий от администраторов
- Поздняя доставка старого сообщения не откатывает preview/дату чата, а старое исходящее эхо не снимает непрочитанное более нового входящего

## Проверки

39 серверных тестов на синтетических данных: реальная блокировка SQLite второй сессией, быстрое принятие/сохранение, повтор после снятия блокировки, один экземпляр сообщения и корректный unread, восстановление после открытия БД заново, payload больше старого лимита hook_log 8000, авария между двумя COMMIT, два worker одновременно, ошибка первого подключения, ошибка/лимит хранилища, аутентификация, приватность, очистка только завершённых, история/статусы/диагностика и параллельная запись при проверке оплат

Отдельный HTTP-сценарий tests.test_comms и существующий MAX-сценарий пройдены с подменой внешних отправок. Chromium: предупреждение появляется/скрывается, защита от запоздалого ответа поиска сохранена. Реальных сообщений/вебхуков в production для теста не создавали. Публикация и работа нового worker в production требуют отдельного подтверждения
