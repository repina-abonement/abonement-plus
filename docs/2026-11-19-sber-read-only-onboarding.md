# Подключение выписки Сбера к контролю оплат

## CRM-151 / CRM-164 — Sber API активирован, подключение CRM подготовлено (19.11)

- **Подтверждено Юлией:** сервис Sber API активирован. Это выполнение шага владельца в банке, не подтверждение чтения выписки сервером CRM. ОФД сегодня уже оплачен, ожидается зачёт платежа/активация; не просить повторно оплатить или заново выяснять уже сообщённый факт. Заказ на скриншоте ещё ожидал оплаты.
- **Код:** защищённая форма «Чеки → Подключение → Сбер Бизнес» только для admin; client_id/secret и P12 передаются через HTTPS прямо CRM, не через чат. Одноразовый OAuth state привязан к руководителю, срок15мин; фиксированный callback и банковский адрес. Разрешения только openid/accounts/GET_STATEMENT_ACCOUNT/GET_STATEMENT_TRANSACTION, банковские платёжные права не запрашиваются. Секреты/P12пароль не возвращаются в UI/аудит.
- **Хранение/TLS:** секреты и обновляемая пара токенов в отдельной приватной директории рядом с рабочей БД (700/600), атомарная запись и блокировка потоков/процессов. P12/пароль после проверки не сохраняются; PEMключ600. Собственный проверяемый mTLSконтекст с официальной цепочкой Сбера, hostname/TLSverification включены; сертификат не подставляется в запросы к другим источникам. Privateхранилище исключеноизgit.
- **Сервер:** независимый incoming_sber каждые10мин, обновление access/refresh без браузера, чтение всех доступных разрешению счетов; сегодня/вчера плюс сохраняемый проход31дня. Все страницы проверяются, стабильный uuid+счёт, суммы/валюты/даты, запрет подмены URL, общий лимит5TPS. Нормальное transactions=[] неошибка; неизвестный ответ неполной выписки не считается нулём. Поступления сохраняются в обзор, оплаты CRM и чеки не создаются. Ошибка Сбера не останавливает Точку/PayKeeper/ОФД.
- **Проверки:** 142 профильных серверных теста и 24 проверки формы в Chromium прошли. Чтение статусов использует атомарный снимок без ожидания сетевой ротации ключа; callback погашает OAuth state до блокировки приватного хранилища и запрещает HTTP внутри транзакции SQLite. Локальные банковские контракты, реальные HTTPмаршруты/права, отсутствие долгой SQLiteтранзакции и конкурентная запись, TLS/файлы/маскирование, OAuthповторы/срок/ротациятокенов, пагинация/сбойисточника и браузернаяформа. Подавление OAuthquery в приложении и точном nginxlocation; конфигпередreloadпроверяетсясоткатомприошибке. Это тесты на синтетических данных, не банковское подключение.
- **Осталось вручную владельцу:** в карточке отдельного промышленного сервиса CRM указать redirect_uri https://ab-plus.ru/api/sber/oauth/callback, получить client_id/secret и сертификатP12, сохранить их в защищённой формеCRM, нажать «Разрешить чтение в Сбере». Затем сервер должен реально прочитать выписку, а обзор показать checked_at/число счетов. Ключи/сертификаты/пароли вчатнепросить.
- **Ограничения:** реальные реквизиты/сертификат/согласие ещё не переданы CRM, рабочий ответ Сбера не проверен. Префикс Authorization соответствует официальному контракту конкретного метода и требует промышленной проверки. Полная историческая сверка, подтверждение чека ОФД после зачёта оплаты и автоматическая привязка всех ручных оплат остаются открытыми. Client_secret живёт40дней: автоматической ротации client_secret пока нет, показывается предупреждение о скором истечении; access/refresh обновляются автоматически. Сертификат12месяцев требует перевыпуска. Нельзя обещать бессрочную автономность доступа.

Источники: https://developers.sber.ru/docs/ru/sber-api/specifications/oauth/oauth-authorize-get ; /oauth-token-post ; https://developers.sber.ru/docs/ru/sber-api/specifications/statement/transactions ; https://developers.sber.ru/docs/ru/sber-api/start/tls . Полные публичные схемы использованы при реализации. ReadAcquiringData не требуется.
