## Серверные циклы

- Три независимых потока в службе CRM: PayKeeper, Точка, ОФД. От ChatGPT, ИИ и открытого браузера не зависят. Служба стартует до AI/tasks, каждый источник со своим соединением SQLite
- `payment_control_jobs` хранит начало, завершение, следующий запуск, состояние и короткий безопасный итог. Интервал 10 минут после окончания цикла; максимум 3 оплаты на проход каждого источника. Очередность по последней проверке, успешные оплаты продолжают опрашиваться для обнаружения возвратов
- Короткая атомарная аренда исключает одновременный запуск одного источника несколькими процессами. HTTP не выполняется в write-транзакции. После падения процесса его аренда освобождается по локальному host/PID; после истечения аренды тоже есть повтор. При потере соединения потока оставшаяся его аренда восстанавливается при следующем проходе. Обычное расписание сохраняется при перезапуске
- Старый фоновый `fiscal.run` с возможностью повторного пробития НЕ запускается новым worker. Существующие ручные функции не вызываются. Настройки старой сверки не переписаны
- PayKeeper сохраняет точные первичные реквизиты, SBP IDs и проверенные данные платежа; последние достоверные идентификаторы доступны банку/ОФД и при сбое PayKeeper. Текущая ошибка PayKeeper при этом не скрывается
- ОФД опрашивается независимо по точным ФН/ФД/ФП, сумме и типу операции. Сохраняются собственное время и очищенная причина HTTP-ошибки, включая `403 Kkt is not paid`. Неизвестный формат или отсутствие результата не равны отсутствию чека
- Точка сохраняет `403 ReadAcquiringData` и результат выписки раздельно. После исправления ключа/лицензии очередной цикл повторяет запрос без ручного запуска

## Строгое подтверждение зачисления

`settlementproof.prove` допускает положительный результат только для однозначной операции SBP в полном блоке реестра:

1. Исходный PayKeeper payment получен, сумма совпала, известный refund_amount равен нулю
2. Точный `operationId` входит в блок реестра; нет дубликатов операций или неоднозначных блоков
3. У всех позиций известен статус APPROVED; проверены gross − fee = net для каждой позиции и сумма всех gross = totalAmount
4. Структурированный `paymentId` реестра точно совпал с `paymentId` единственной проводки. Свободный текст, сумма/дата и похожее имя не заменяют эту связь; block.paymentId не переименовывается в выдуманный payoutId
5. Проводка Booked / Credit / RUB, известный transactionId и дата отражения; сумма всей проводки равна сумме net всего блока
6. Неполная выдача реестра/неизвестная пагинация, другая валюта, неопределённая комиссия, возвратный или промежуточный статус не дают подтверждения

**Оставшееся ограничение:** рабочее соответствие полей и полного состава реестра должно быть проверено после снятия 403. Использован имеющийся probe на основе ранее изученной вторичной OpenAPI-схемы; реальные рабочие ответы всё ещё нужны. Подтверждение блоков с возвратами не реализовано: текущая схема не подтверждает отдельные суммы/комиссии/банковские ссылки возврата; такие блоки остаются в проверке с явной причиной. Нельзя считать refund_amount нулём при отсутствии поля. Сбер и ручные несвязанные оплаты остаются открытыми задачами.

## Интерфейс и проверка рабочего платежа

«Оплаты» → «Контроль оплат и чеков»: состояние каждого серверного цикла, последнее завершение/следующий запуск. По каждой оплате — PayKeeper, зачисление и ОФД раздельно, собственные времена и причины. Состояние запуска не подменяет подтверждение платежа.

Добавлен GET `/api/fiscal/control-payment?provider_payment_id=11534` только для руководителя: читает исключительно сохранённые данные, возвращает `control_version: 2`, цепочку и циклы; не вызывает поставщиков и не меняет БД. GET `/api/fiscal/source-status` также показывает циклы; прежний GET `/api/fiscal/paykeeper-payment` остаётся живой диагностикой чтения.

Контрольный платёж: №11534 / 1350 ₽. По последнему подтверждённому рабочему отчёту зачисление не найдено, retailers 403 / ReadAcquiringData, ОФД 403 / Kkt is not paid. Нового рабочего ответа в этой сессии нет. Для сквозной рабочей проверки нужны авторизованное чтение состояния после публикации и восстановленные права Точки/ОФД. Не включать старую сверку и автопробитие.

## Локальная проверка

Проверены отдельные источники при зависании PayKeeper, отсутствие SQLite write-lock во время HTTP, повтор после 403 обоих источников без настройки/ручной кнопки, сохранение расписания после нового соединения, восстановление истёкшей аренды и аренды погибшего процесса. Отдельно реально остановлен subprocess во время проверки и запущен новый процесс с той же временной БД: проверка восстановлена.

Сквозной тест трёх настоящих циклов на одном ранее созданном тестовом платеже: PayKeeper → полный реестр из двух операций и комиссия → Booked проводка → точный чек ОФД → complete; последующий обнаруженный возврат убирает complete. Проверены неверные/дублирующиеся ID, неполный блок, комиссия, валюта, pending, неизвестные/частичные возвраты. 92 профильные проверки пройдены (включая импортируемые fixture-наборы), legacy fiscal завершён с кодом 0, Chromium настоящего JS проверил сводку/причины/фильтр/навигацию и состояние циклов; синтаксис Python/JS и git diff --check пройдены. Авторизованный рабочий рестарт не выполнялся.
